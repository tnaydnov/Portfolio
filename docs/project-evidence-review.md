# Project evidence review

**Research date: 12 September 2026.** This review consolidates source audits of eleven projects and a new collection of authentic local product recordings. It explains what the portfolio can substantiate, why particular workflows were selected, and where source inspection or a successful local scenario stops short of a broader claim.

The strongest editorial reading is consistent across the projects: Tomer works on software that makes complicated state understandable to people. A learner can see why a program failed; an instructor can manage a shared activity; a job seeker can connect an opportunity to their own documents; an event guest can recover a message after losing connectivity. The earlier engineering projects expose the underlying interests in permissions, state transitions, concurrency, integration and visual computation. This is an interpretation of the evidence, not a claim about adoption or measured user outcomes.

## Method and provenance

Four evidence levels remain separate:

1. **Inventory:** enumerate tracked paths, classify source, tests, configuration, documentation, generated/vendor material and binary assets. A file count is not a count of original contributions or reviewed assertions.
2. **Structural review:** read text to index declarations, routes, dependencies, configuration and incomplete paths. This locates subsystems; it does not establish their correctness.
3. **Semantic review:** trace relevant control flow, data boundaries and assertions in selected files or, for the smaller repositories, the complete authored implementation. The individual reports specify coverage.
4. **Demonstration:** exercise a named scenario through the original interface and its isolated local backend, with fictional records, then inspect the resulting UI and relevant persisted state. This establishes that scenario at the recorded revision, not every feature, provider integration or deployment condition.

The main product audits combine these levels. The seven earlier studies are source-only; committed output traces are identified as historical artifacts. No current full application test-suite result, security certification, scale benchmark, model-accuracy result or production-provider outcome is inferred from source or screenshots. Generated code, dependency locks, model weights, photographs and data fixtures do not count as authored implementation. Private uploads, credentials and operational log contents are not published.

## Main product stories

### Arc: learning, shared state and preparation

**Chosen capabilities:** personal learning environments; expressive student work; instructor-led shared activity; syllabus preparation with visible readiness. These show different actors and different kinds of state instead of repeating dashboard views.

The student scenario switches among five persisted themes, constructs a native five-node flowchart, completes six matching pairs and inspects saved work and reflection cards. The classroom scenario uses an instructor and two independent student sessions: both students answer the second question, the instructor advances the activity, and the ended session and participation records are checked. The runtime uses Arc's three-second polling fallback; it demonstrates shared state, not a tested WebSocket connection. The preparation scenario drafts three lessons containing nine activities from 26 fictional source activities, edits a lesson title, examines source provenance and reveals that all nine still need teaching material. It stops before publishing or assigning that draft. [Full Arc evidence](../public/media/projects/arc/depth/research.md).

The architectural story is the separation between activity-specific work, submissions, reusable content packs, assignment and release. Submission handling prevents a late autosave from silently recreating a draft after submission; the shared quiz validates membership, question identity, duplicate answers and timing. Smart drafting ranks existing content using rules and preferences. It is not generative pedagogy, a strict constraint solver or evidence that student feedback automatically rewrites curriculum. Private source: `src/app/Platform/Domain/Submission/SubmissionService.php:34–44`; `Domain/QuizBattle/QuizBattleAnswerService.php:1–95`; `Domain/ContentBuilder/SmartDraftGeneratorService.php:1–221,386–440`; `Domain/ContentBuilder/ContentPackDraftPublishingService.php:1–141`.

The films are **Learning worlds and making** (33.5 s), **Live classroom: two sides** (32.5 s), and **Syllabus: from intent to review** (32.0 s). Source-only breadth includes other activity handlers, peer review, scoped analytics, account merging and external coding/game launches. The 21 canonical task types have heterogeneous handlers; this is not 21 demonstrated complete editors. A newly opened diagram version appeared blank during capture, so automatic diagram carry-forward is not claimed. Neither readiness warnings nor analytics imply measured learning improvement or a clinical assessment. [Arc coverage, runtime limits and source paths](../public/media/projects/arc/depth/research.md).

### Browser Coder: help a learner reason about the program

**Chosen capabilities:** actionable feedback; inspectable execution state; code-linked graphics; portable multi-file projects. These distinguish a teaching workbench from a generic browser editor.

The learning film shows a missing Python colon, a narrow explicit repair, and three teacher-authored checks. Two pass and one exposes integer division; the learner changes `//` to `/`, after which all three pass. The state film inspects real loop values and recorded pauses. The graphics film executes Python Turtle, then replays and scrubs its drawing commands. The web film previews a fictional HTML/CSS project and opens a published share in a fresh recipient context; editing that local copy leaves the original server snapshot unchanged. The sample website's design is input to the IDE, not built-in Browser Coder UI. [Full Browser Coder evidence](../public/media/projects/browser-coder/depth/research.md).

Three decisions explain the experience. A shared pipeline validates the entire project and coordinates six language adapters, job directories, processes, streamed results and cleanup. A per-document save coordinator marks the revision actually written, preserving newer unsaved edits. Debug history retains up to 500 pause snapshots for inspection without reversing the live process. The host protocol serializes initialization and reconciles files by path, while allowing separate controls for editing, structure, running and panels. [Execution pipeline](https://github.com/ninasokolov8/browser-coder/blob/7d3cae91ff9cc73001d7fcfa0aa3b315cebb2aeb/server/execution/pipeline.mjs#L127), [revision-aware persistence](https://github.com/ninasokolov8/browser-coder/blob/7d3cae91ff9cc73001d7fcfa0aa3b315cebb2aeb/src/workspace/persistence.ts#L229), [stop history](https://github.com/ninasokolov8/browser-coder/blob/7d3cae91ff9cc73001d7fcfa0aa3b315cebb2aeb/src/features/debug/history.ts), [host initialization](https://github.com/ninasokolov8/browser-coder/blob/7d3cae91ff9cc73001d7fcfa0aa3b315cebb2aeb/src/integrations/stepup.ts#L178).

The four edits are **Learning journey** (30.4 s), **State journey** (27.6 s), **Graphics journey** (22.1 s) and **Web journey** (20.7 s). Their real execution evidence is Python plus the web preview/share flow; six adapters in source does not mean six toolchains were filmed or verified. Hidden harnesses are a UI convention, not secret files. Jobs have separate directories but share the service's OS user; configured Linux containment is around the API replica, not a container per learner. Interactive runs disable the ordinary wall timeout. Preview CSP still allows permitted browser network requests. These boundaries prevent an unsupported hostile-code-isolation claim. [Process lifecycle](https://github.com/ninasokolov8/browser-coder/blob/7d3cae91ff9cc73001d7fcfa0aa3b315cebb2aeb/server/execution/process-runner.mjs), [preview policy](https://github.com/ninasokolov8/browser-coder/blob/7d3cae91ff9cc73001d7fcfa0aa3b315cebb2aeb/server/previews/headers.mjs#L139), [detailed execution limits](../public/media/projects/browser-coder/depth/research.md).

Explorer rename failed through both menu and keyboard paths; the focus/blur conflict remains unfixed and is excluded from successful footage. Nested Python debugging has path-recognition limits, and Turtle callbacks are not a full desktop event implementation. Tomer is a **collaborating engineer**, not the repository owner or sole author. The C# debugger/restore, debugger teardown, Turtle behavior and host-diagnostics commits establish concrete contributions while retaining their co-author context. [Representative contribution](https://github.com/ninasokolov8/browser-coder/commit/a91b62221e571c02413bbce5391a89ea183b56a3).

### Applytide: bring an opportunity into a personal workspace

**Chosen capabilities:** extension-based intake; owned job/document context; transparent document feedback; source-backed provider and cost boundaries. These add substance beyond moving an application between pipeline columns.

The first film captures a fictional Northstar Studio posting through the original extension into Alex Morgan's real isolated account. The original extractor consumes the page's DOM/JSON-LD; the saved opportunity's identifier is verified against the backend. The second previews an uploaded fictional PDF résumé, selects a saved Fieldnote job **inside the analysis dialog**, and inspects persisted scores and keyword feedback. This path passes the selected job ID; the separate Documents-page “Compare to Job” shortcut does not pass it through and is not represented as working comparison. [Full Applytide evidence](../public/media/projects/applytide/depth/research.md), [extension extraction/cache orchestration](https://github.com/tnaydnov/Applytide/blob/a040d14d5c45491e3db1651c0d4daa67a218c32f/chrome-extension/background.js#L1549).

The local analysis is an **honest heuristic fallback, with no paid model call**. The recorded overall score is 64; component results include formatting 80, keyword match 34 and readability 60. These are implementation-specific feedback values, not validated ATS or hiring predictions. A persistent editorial label qualifies the interface's “Advanced AI Analysis” wording. The cache binds document content, job content and identifiers, so the architecture is more specific than a generic “AI résumé tool.” [Analysis implementation](https://github.com/tnaydnov/Applytide/blob/a040d14d5c45491e3db1651c0d4daa67a218c32f/backend/app/domain/documents/service/analysis.py), [content-sensitive cache](https://github.com/tnaydnov/Applytide/blob/a040d14d5c45491e3db1651c0d4daa67a218c32f/backend/app/domain/documents/service/cache.py#L73).

The films are **Extension intake** (25.7 s) and **Role-aware document review** (30.5 s). Both use the real isolated backend; only capture-specific origins and local infrastructure setup differ from the original checkout. Extension compatibility across arbitrary job boards, paid-provider interview/cover-letter results and outbound reminders were not demonstrated. A provider-budget check allows requests when its Redis lookup fails, whereas the per-user AI rate limiter rejects requests when its Redis dependency fails; together these are intended operating controls, not a hard all-failures spend guarantee. [Budget failure boundary](https://github.com/tnaydnov/Applytide/blob/a040d14d5c45491e3db1651c0d4daa67a218c32f/backend/app/infra/external/llm_tracker.py#L60), [rate-limit boundary](https://github.com/tnaydnov/Applytide/blob/a040d14d5c45491e3db1651c0d4daa67a218c32f/backend/app/infra/security/rate_limiter.py#L441).

Supporting probes exposed a Remote filter returning no results, notification preferences reporting success despite a 422 response, incomplete reminder/2FA paths and empty analytics. Those outcomes were not dressed up as successful feature scenes. The selected extension result also retains its imperfect extraction: description repetition and an empty skills list. Applytide is presented as an archived personal project restored locally, not an operated public SaaS with measured user adoption. [Coverage, excluded probes and operating status](../public/media/projects/applytide/depth/research.md).

### Eventa: one event, four distinct audiences

**Chosen capabilities:** customer personalization; organizer intake and review; guest connection and recovery; separate operator oversight. The customer marketing illustration is not substituted for the actual guest application.

The customer film uploads and crops an original background, previews poster choices and inspects an editable order summary; it stops before submitting an order. The organizer film acknowledges consent and validates 14 CSV rows into 12 valid, one duplicate and one invalid record, then examines invitation preparation. The final report uses a separate ended-event fixture; the edit does not imply that the same event completed in seconds. Phone encryption is checked in the database, but invitation previews are not evidence of an SMS send. [Full Eventa evidence](../public/media/projects/eventa/depth/research.md), [background-crop implementation](https://github.com/tnaydnov/eventa/blob/103f9daeb56d30db13c7277a7d8259f2ed9d287c/src/app/_components/wizard/steps/StepBackground.tsx#L152), [organizer import endpoint](https://github.com/tnaydnov/eventa/blob/103f9daeb56d30db13c7277a7d8259f2ed9d287c/src/app/api/guest-portal/%5Btoken%5D/route.ts#L374).

The guest film uses two actual browser sessions. A text message fails while offline, remains in the durable outbox, and reaches the other guest after reconnection; exactly one matching database message is verified. Blocking then records the relationship context and removes the pair's conversation and messages. This makes recovery and safety actions observable rather than merely labeling the app “realtime.” [Durable outbox](https://github.com/tnaydnov/eventa/blob/103f9daeb56d30db13c7277a7d8259f2ed9d287c/src/lib/chat-outbox.ts), [block behavior](https://github.com/tnaydnov/eventa/blob/103f9daeb56d30db13c7277a7d8259f2ed9d287c/src/app/api/secure/blocks/route.ts#L36).

The films are **Customer personalization** (21.4 s), **Organizer journey** (29.5 s) and **Guest connections** (22.2 s). They preserve the original Hebrew interface with English editorial guidance and use fictional events and profiles. Local schema/bootstrap and image-handling compatibility adjustments are documented; this is not an out-of-the-box setup claim. Orders, payments, email/SMS and paid AI were not sent. Source-based payment reconciliation detects anomalies; it does not automatically repair money movement. Account deletion anonymizes identifying data while retaining specified activity records, so immediate complete erasure would be inaccurate. [Account-deletion semantics](https://github.com/tnaydnov/eventa/blob/103f9daeb56d30db13c7277a7d8259f2ed9d287c/src/app/api/account/delete/route.ts#L64).

Unresolved observations include an unreliable PDF-download interaction, missing numeric glyphs in the endpoint-produced PDF and hourly report bars that did not render. Those artifacts were excluded from selected success media. Full report screenshots remain accessible, while focused compositions emphasize the working funnel and audience sections. Source also shows that the consent acknowledgement is not a server-enforced prerequisite, and some encrypted-contact search/deduplication paths remain incomplete. [Reporting limitations and excluded artifacts](../public/media/projects/eventa/depth/research.md).

## Media selection and presentation rationale

The new depth manifests select **58 assets: 46 screenshots and 12 films**. This count excludes previous-tour media, posters, caption/chapter files, technical diagrams, editorial boards and generated derivative crops. It counts selected manifest entries, not every capture attempt or file on disk.

The editing is deliberately more than a caption over a screen recording. Context frames establish the user and task; original-pixel crops expose the code line, score, saved result or recovery state that proves the claim. Chapter cuts remove setup and idle time, while holds give dense results time to be read. Browser Coder's web story holds the genuine preview and shared-copy stills. Applytide places the real posting and extension together and accelerates part of intake to 1.25×; analysis receives focused result holds. Arc alternates student, instructor and preparation contexts. Eventa clearly separates desktop organizer/customer views from a portrait guest session. Each film's chronology is a selected scenario, not an assertion of unedited elapsed time or continuous identity across separately labelled fixtures.

Lossless compositor PNG sources preserve small interface text before H.264 delivery. Editorial slates, explanatory labels and annotations sit outside or alongside original application pixels. No AI-generated replacement interface, fabricated successful output or live-provider response is used. Source-pixel focus rectangles support readable detail compositions while original screenshots remain accessible in the viewer. Source-only architecture diagrams use different visual treatment and explicit interpretation; they are not presented as application screenshots. The synthetic user records, uploaded samples and deliberate errors support reproducible demonstrations without exposing real pupils, applicants or guests.

Four additional **3200 × 2000 presentation boards** provide an immediate overview: Arc combines the student environment, flowchart and syllabus; Browser Coder combines drawing, explanation and state; Applytide connects the saved opportunity, extension confirmation and document breakdown; Eventa connects the guest, customer and organizer views. These are authored HTML/CSS compositions of original screenshot crops, with captions outside source pixels, and are counted separately from the 58 evidence assets. Each public capture manifest records the source images, pixel crop rectangles and SHA-256 hashes.
